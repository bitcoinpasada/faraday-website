The rule

Faraday follows published specifications: BIPs, SLIPs, RFCs and conventions other wallets already use. Where a specification has an established implementation, Faraday uses it as a library instead of writing its own.

The rule for what the app offers (owner, 2026-10-23; written in the decision F109). From STANDARDS §0.

  1. A published standard, followed and checked. A wallet kind, key method, format or signing procedure is in the app when it follows a published standard (a BIP at Complete or Deployed, a SLIP, an RFC, or a convention other wallets already use), is built in full or names the part it leaves out, and is checked against that standard's vectors or an implementation Faraday did not write (F79's cross-check, other wallets; F160).
  2. Established implementations first (F178). Faraday uses an established implementation wherever one exists for what it needs: the standard's own reference implementation, or the implementation the ecosystem relies on, published by a project F71 trusts. It writes its own only where none exists or none fits its rules for keys. Each piece it writes says which of four reasons holds (Faraday's own specification; no established implementation; one exists but does not fit the key rules, and which rule; only the part used is written). A new piece written here, or a library that is not established, is a decision.
  3. A draft that is stable enough. A draft whose text has held still, that has outside implementations and that Faraday's cross-check agrees with, can be in the app; the table says it is a draft (codex32, BIP 93).
  4. Faraday's own, conservative. Where no standard exists, Faraday's own format or rule is in the app when it fails closed (a refusal, a record layout) and a decision records it. A cryptographic specification of Faraday's own is in the app only once it has been reviewed, or when it can only add to a standard's strength (mixing a person's own randomness into the system's); §7 lists them for outside review.
  5. No way past a check without a legitimate reason (F136). A check that keeps a person's keys or money safe has no way past it unless a decision names a real case that needs one. Where one does, the way past is a hold, and the hold says what is not checked and the case it is for. A transaction that can never be valid, or a claim about the person's own key that is false, is refused. A note that keeps nothing safe (dust, address reuse) is a note, not a check, and needs no hold.
  6. Checked against an implementation Faraday did not write (F160). Anything that makes or reads a key, a secret, a seed or backup encoding, an address, a signature or a transaction is checked against an implementation Faraday did not write: an F79 cross-check area against a pinned outside reference (tools/crosscheck/README.md), or the other tool itself end to end (Bitcoin Core, gpg, openssl); and against the standard's published vectors where they exist. A second implementation written by Faraday's own authors, from the specification or from the code, is Faraday's own: wherever the check is described it is said to be compared with an implementation Faraday's authors wrote and not checked against an outside source, and each action's independence in the manifest says whether its cross-check compares with others' code, Faraday's second version, or both (F177, F179). Today several areas compare with such second versions (docs/CROSSCHECK.md §10.7 lists them and what replaces them). Where no outside implementation can exist (Faraday's own formats and procedures), the action is labelled "own specification, not yet reviewed outside Faraday" until an outside party reviews it, by an implementation of its own written from the specification or by reproducing the published vectors (§7). Exceptions: flow and screen logic, and plumbing that carries bytes it does not interpret (the backup plan, the file envelope's framing), rest on Faraday's own tests; a small standard its published vectors cover in full (TOTP's RFC 6238, the Diceware lists' digests) may rest on them. New cryptographic code lands with its check; a gap found later is closed before 1.0, not a block on every release.
  7. Otherwise it waits in the repository. Work on a feature whose standard is unpublished, or whose specification is Faraday's own and not yet reviewed outside Faraday, stays in the repository, built and tested but compiled out of the app, until its standard is published or it is reviewed.
  8. Scope (F116). Faraday is an offline signer and keeper of keys: a person's Bitcoin wallets and their backups first, and the other keys a person keeps offline beside them: an OpenPGP key (signing with GnuPG), TOTP secrets, Secure Boot keys. A new kind of key or signature comes in on the owner's word, recorded in DECISIONS; the list below names what is left out.

How it's checked

F79, docs/CROSSCHECK.md §10. Faraday's own Rust answers requests, and pure-Python references recompute every answer, over every published vector and a corpus of random inputs drawn from a fixed seed. The first disagreement stops the area and is printed with its inputs and both answers. Some references are others' code, code Faraday did not write; others are Faraday's second version, a second implementation Faraday's authors wrote, over others' code or alone, and those are not checked against an outside source (F160, F177, F179): "Others' code and Faraday's second version" below says which, per action.

What runs

just crosscheck is a recipe of its own, not part of just. A test-only Rust command, never shipped in an image or app, reads one request a line on stdin and answers one line on stdout: the operation, its inputs and Faraday's result. A Python script sends the requests, recomputes each result with the area's reference (code from §3, or a second implementation Faraday's authors wrote, §10), and stops at the first disagreement, naming the operation, the inputs and both results.

The inputs are every published vector under tools/vectors/ and a corpus of random inputs drawn from a fixed seed, so that a failure is reproduced by running again. Secrets in the cross-check are test data only.

CROSSCHECK §10.1

The self-test

Before every run, each area runs against the Rust command started with FARADAY_CROSSCHECK_SABOTAGE=<op>, which changes every answer to that one operation. The run fails unless every area reports that operation as a disagreement: a cross-check that cannot fail is worse than none.

The stamp

A passing run writes a stamp file beside the cross-check: one hash over the crypto sources and the crypto crates' entries in Cargo.lock, and the versions of the references and the Python interpreter it ran with. just lint hashes the same inputs and fails when they do not match the stamp, with "crypto changed since the last cross-check: run just crosscheck". The check costs about a second; the cross-check itself runs only when it fails. The stamp is committed with the change that made it pass. It is a record, not a security control. It also holds each area's corpus case count for that run, one cases <area> <count> line each.

What the stamp covers

core/faraday-crypto, core/faraday-bip, core/faraday-psbt, core/faraday-entropy, core/faraday-backup, faraday/faraday-vault, the signing and derivation code in faraday/faraday-keys, and the Cargo.lock entries of rust-bitcoin, rust-miniscript, secp256k1 and the RustCrypto crates. A version bump of one of those crates counts as a crypto change.

Before a release

just crosscheck --fresh, with a new random seed and about ten times the random cases. A disagreement it finds keeps its seed and inputs as a new vector.

Before every release, every target of fuzz/ and faraday/fuzz/ runs for 10 minutes, as many at once as there are cores (just fuzz-release). A crash, an out-of-memory or a timeout fails the run and names the input. The release notes quote the run's record.

Other programs, end to end

Where another program does the same job, Faraday's output goes through it: Bitcoin Core 31.1 for wallets and PSBTs (faraday/tools/core-check.py and the cross-check's addr, psbt, sign and miniscript areas), GnuPG 2.4 and paperkey 1.6 for GPG keys (faraday/faraday-pgp/tests/gnupg.rs, faraday/faraday-pgp/tests/paperkey.rs), OpenSSL and sbverify for Secure Boot keys (faraday/faraday-sb/tests/judged.rs), pykeepass for KeePass files (the cross-check's kdbx area), and other wallets' own files (faraday/faraday-core/tests/all/interop.rs). Dependencies

just lint runs cargo vet --locked (F71): every outside crate is trusted by a publisher F71 names (rust-bitcoin's, RustCrypto's, dalek's and others), covered by an imported audit, or an exemption whose page in docs/deps/ says "not reviewed". Every direct dependency has a page there. Cargo.lock pins every source by its checksum, and every build and check passes --locked. cargo deny check, also in just lint, checks advisories, licences, duplicates and sources against deny.toml.

Outside review

Faraday invites audits from experts and AIs and publishes each one at https://faradayoffline.app/audits/. An entry has the submitter's summary, Faraday's short response, and links to the full prompt and output, to Faraday's reply on the issue, which gives the verdict on each finding, and to anything else written about it. Critical and high findings are sent privately and published once fixed. A hash posted on the day they are sent shows that the file published later is the one that was sent.

Faraday's own specifications, which no outside implementation checks, are listed for review in docs/STANDARDS.md §7, ranked by how much a mistake would cost, and called for in docs/AUDIT-SUBMISSIONS.md §10.

Offline, and pinned

The cross-check fetches nothing, ever.

  • The pure-Python references (the BIPs' reference code, Bitcoin Core's functional-test framework, python-mnemonic, python-shamir-mnemonic). are copied into tools/reference/, each with its source (the git commit in the BIPs repository, Core's release tag, Trezor's release) and its SHA-256. The cross-check refuses to run when a file does not match its hash. Adding or updating one is a reviewed commit. A first copy is checked against something other than the web's certificates: the BIPs repository's commit hash, Core's signed tag, Trezor's signed release.
  • Argon2id, XChaCha20-Poly1305, HKDF-SHA256 and ChaCha20. come from the Linux distribution's packages (argon2-cffi, PyNaCl and PyCA cryptography: python3-argon2, python3-nacl, python3-cryptography or their equivalents), installed once on the machine that runs the cross-check and verified by the distribution's signatures, not by pip. Their versions are in the stamp.
  • python-ecdsa (python3-ecdsa, by Brian Warner and Hubert Kario; MIT, pure Python). is the same kind of package, checked for presence like argon2-cffi (the run stops without it) and its version is in the stamp. With btclib's curve it is the second lineage beside libsecp256k1 (tools/crosscheck/lineage.py, owner, 2026-10-29): it makes every ECDSA signature the sign and msg areas expect again under plain RFC 6979 and verifies the low-R ones; btclib verifies every BIP-340 signature and makes it again where the auxiliary randomness is known, and verifies MuSig2's aggregate. Core's key.py and secp256k1lab are still asked.
  • python-bip380. , Antoine Poinsot's miniscript, is copied from its signed commit (tools/reference/miniscript/README.md), the signature checked against the key Bitcoin Core's guix.sigs publishes; two shims stand in for the libsecp256k1 packages it imports.
  • Bitcoin Core's functional-test framework. is copied from the release tag v31.1 (tools/reference/core/); BIP-32 is written in the areas from the BIP's text, checked against the BIP's own vectors first.
  • HWI's PSBT reader (hwilib/psbt.py and the modules it imports). is copied from a signed commit on HWI's master, the signature checked against the key Bitcoin Core's guix.sigs publishes (tools/reference/hwi/README.md, which says why not its last release); a shim stands in for typing_extensions.
  • btclib, ecc and btclib-wallet. are their published wheels, byte for byte, pinned by the SHA-256 btclib-wallet's uv.lock names and compared with the tagged commits (tools/reference/btclib/); the run unpacks them after the hash check and uses btclib's own curve, never libsecp256k1.
  • btcd's BIP-322 (pull request 2521, unmerged, at its head commit). is a Go module vendored with go mod vendor (tools/reference/btcd-bip322/), built by run.sh with GOFLAGS=-mod=vendor, GOPROXY=off and GOTOOLCHAIN=local.
  • Bitcoin Core v31.1 itself (bitcoind and bitcoin-cli). is a binary reference, required (owner, 2026-10-29). Its release tarball is over the tree's 2 MiB limit and is not in the tree, nor in Ubuntu's packages. So the official tarball for the machine (x86_64 or aarch64 Linux) is pinned by its SHA-256 in tools/reference/core/release.pin, listed in references.sha256 like a vendored file. A person fetches it once with tools/crosscheck/fetch_core.py, which requires the release's SHA256SUMS to carry good signatures from at least five of the builders whose keys guix.sigs publishes (at a pinned commit), and no bad one, and the tarball to match both SHA256SUMS and the pin. It is kept outside the repository, in the folder FARADAY_BITCOIN_CORE names (default ~/.cache/faraday/bitcoin-core). Every run hashes the tarball against the pin and unpacks the two programs from it into a scratch folder, so what runs is what was checked. A missing or mismatched tarball fails the run, naming it. The node runs on regtest with -networkactive=0 -listen=0 -connect=0, no seeds, no wallet and a scratch datadir, RPC on loopback only, with a cookie. It is stopped and its folders deleted on every way out of the run, and killed if the run dies. The stamp records Core's version and the tarball's SHA-256, and just lint fails when they are not the pinned release's.
  • No network. Python runs in a network namespace whose only interface is loopback, which the run brings up for Core's RPC, and refuses to run when any other interface is there. The Rust command is built with --offline --frozen. Anything that tries to fetch fails instead of downloading.

What it does not catch

  • A library changed after the build, or a fault on the machine that signs; only option B catches those.
  • A misreading of a BIP that both implementations share; the BIPs' own reference code and the published vectors are the defence there.
  • A misreading shared by Faraday's Rust and a second implementation, in Python, written by Faraday's own authors, which is likelier than between strangers. Where the reference is Faraday's own (§10), the published vectors are the only defence, and an action with no vectors has none.
  • A flaw in a spec Faraday wrote itself (the vault, own randomness, the entropy procedures, the Demo roller): both sides follow the same text. Only an outside review finds it.
  • A blind spot of the corpus generators, which Faraday's authors wrote too: what they never ask is never compared.

Where Faraday is stricter than the standard

Recorded in a decision

  • A passphrase is printable ASCII, at most 256 bytes. BIP 39 allows any NFKD text, so a wallet made elsewhere with another passphrase cannot be restored here; a letter outside the range typed into a passphrase field is refused. (F155)
  • Restore takes a seed for a wallet's key slot only when its whole extended public key at the slot's path matches the wallet's, not the four bytes of its fingerprint. (F155)
  • A multisig key with no origin is refused where a policy reads it. (F155)
  • The list of reasons is closed: a new reason is a new variant, seen in review. (F70)
  • Only BIP 341's H, or an extended key over H, counts as an unspendable internal key. (F132)
  • A SLIP-132 version is checked against the script and the path around the key. (F155)
  • A Caravan file whose startingAddressIndex is not 0, and an Electrum multisig keystore with no fingerprint, are refused. (F155)
  • Script-path spends of a musig() wallet are refused; only the key path is built. (F155)
  • The stick and the Pi read /dev/random; the Pi's generator is mixed, not credited. (F102)
  • The stick's kernel credits neither the CPU's RDRAND nor the firmware's seed; both are still mixed in. (F86)
  • Added randomness never replaces the system's bytes. (F86)
  • A key origin of more than 16 steps anywhere in a PSBT is refused when it is parsed. (F155)
  • Change under an unloaded key, or at a path under no loaded account, counts as a payment to others. (F136)
  • A script of several keys is signed only for a registered wallet that holds a loaded key. (F135)
  • A miniscript or a taproot tree of one key is signed only through its registered wallet. (F141)
  • A SegWit v0 input with only a witness UTXO in a transaction of several inputs is refused, which BIP 174 allows. (F155)
  • The signed-amount memory refuses one transaction stated again with other amounts. (F155)
  • NONE, SINGLE and non-standard sighashes are refused for signing; ALL with ANYONECANPAY is signed after a caution. (F136)
  • A WIF key is never loaded as a key or kept: it lives for one sweep. (F171)
  • A key comes from the PSBT's origin only, under the master key's fingerprint; a key whose derived public key differs from the one named, or that the script does not hold, is refused, and an origin under an account's fingerprint matches no key. (F155)
  • Only a high fee and an absurd fee rate can be held past; every other danger refuses. (F136)
  • The secret nonce is held in memory for its one session and never serialised. (F109)
  • Every limit fails closed: a frame, a count or a size past it is refused. (F155)
  • Recovery is from exactly k shares only. (F90)
  • A further share is derived only from exactly k strings at an index not in use. (F90)
  • Correction is opt-in, off whenever the form opens, proposes only where the correction is unique, and is never applied: the person types the changed boxes again. (F94)
  • A character outside the bech32 alphabet is not read as an erasure, and more than 8 erasures not in one run are refused; BIP 93 makes the first optional, and python-codex32 accepts both. (F155)
  • No code is drawn for a 74 or 127 character string, and none is read but as plain text, until the profile's author publishes a profile for them. (F95)
  • Shares with an iteration exponent above 5 are refused; a split writes exponent 1 with the extendable flag set. (F90)
  • A split with a group threshold of 1 over several groups is refused. (F90)
  • Secrets above 256 bits are refused. (F155)
  • A key a PSBT states for an input counts only where the input's script commits to it, which is stricter than BIP 375's reference validator. (F89)
  • The reader limits (lanes exactly 1, passes at most 10, memory 8 MiB to 4 GiB) refuse headers that would cost a guess or an allocation the vault does not state. (F155)
  • Every slot's plaintext begins with 32 zero bytes, the padding fix for key commitment, so a slot that verifies under two keys shows them under at most one (docs/VAULT.md §4, §7). (F159)
  • A slot whose tag verifies and whose commitment block is not zero refuses the whole file, as two slots opening under one key do: this format never writes one (docs/VAULT.md §4). (F159)
  • Signing waits until the backup flow has written every place the key's plan gives it, two or more; GnuPG has no such gate. (F32)
  • Signing takes a hold (F63) and shows the files' names, sizes and SHA-256 first. (F32)
  • The paperkey is computed only while it is held to show, and wiped after. (F32)
  • A restore that cannot reproduce the certificate's own signatures is refused rather than accepted on the public key alone. (F155)
  • Anything not honoured is refused rather than read, so the release check of F134 cannot be satisfied by a signature of another shape. (F134)
  • A boot program is signed only when it is a release's own. (F134)
  • Anything but the release's own bytes with the person's signature is refused by name. (F133)
  • The sheet carries the key only when it is ticked, and holds it only until the sheet is made. (F49)

Not recorded in a decision

  • An extended private key is decoded by Faraday's own strict reader because bitcoin accepts seven of the sixteen serialisations vector 5 rejects.
  • A descriptor record whose paths line is neither /0/*,/1/* nor No path restrictions is refused.
  • The id is all 32 bytes of a hash, so two seeds never pass for one.
  • The reader refuses what BIP 370 marks invalid and keeps every pair as read.
  • A previous transaction is attached to an input only when its id is the spent one.
  • A part of another message, and an empty message to animate, are refused.
  • An envelope is refused unless it is exactly what pack would write for its file.
  • A secret goes to a stick only for the backup-stick reason, and only the part that reason names.
  • Nothing is written to the Outbox until the hold on the secret sheet is held to its end.
  • A secret pasted or scanned where a secret may not go is refused, whatever its form.
  • Spends of SegWit above v1 and sighashes other than ALL are refused.
  • Four tag checks on every open, so timing does not show which slot a passphrase opens.
  • Which passphrase goes with which words is decided by the vault's record, not by a guess; a mismatched fingerprint is not loaded.
  • No key is accepted until the checks pass.
  • Both the compressed and the decompressed sums are checked, and a mismatch after writing is reported as a failure.

Faraday's own specifications, for outside review

Ranked by how much a mistake would cost. The call for an outside review of each, what a reviewer gets and how a review is recorded, is docs/AUDIT-SUBMISSIONS.md §10. From STANDARDS §7.

  1. Makes a vault file of four equal slots from one to four passphrases, with Argon2id, HKDF-SHA256 and XChaCha20-Poly1305, and a ChaCha20 keystream for the salt, the nonces and the unused slots. Faraday's own container with four equal slots, so a file does not say how many slots are in use (docs/VAULT.md §9); unused slots are keystream, one salt serves every slot, and an older copy of a slot still opens. Kept until the outside review. (F158) Adds, changes, copies and makes public the records of an open vault, holding every secret field in a value that wipes on drop. Faraday's own record layouts (docs/VAULT.md §7); a second implementation Faraday's authors wrote from that text, not from the code, reads them; they are not checked against an outside source. (F97) Own specification, not yet reviewed outside Faraday (F160, F177).
  2. Records pointer moves and key presses with time and a running count, and commits them in batches of SHA-256 for the session's randomness. Pointer and key timings are added to the session's randomness, never made into a key on their own. (F86) Keeps the session's seed and pool from the shell's answers, mixes a person's own randomness in, never in place of the system's, and draws the seed of a MuSig2 round. The mixing is Faraday's own specification. (F86) Own specification, not yet reviewed outside Faraday (F160, F177).
  3. Holds a key in memory blinded and on pinned pages; the sealing under a session key built in faraday-crypto is reached by no shipped code. The in-memory seal's nonce is a counter with a prefix derived from the key, because the crate has no random number generator; no shipped code reaches it, so no secret is sealed in memory today. (no decision) Own specification, not yet reviewed outside Faraday (F160, F177).
  4. Turns playing-card draws into entropy as SHA-256 of the draws' indices, one byte each. The procedure is Faraday's own: a card is the index suit × 13 + rank, and the entropy is SHA-256 of those one-byte indices; no other wallet's card mode is claimed to match, and the bits counted assume a well-shuffled deck. (F158) Commits to camera frames as SHA-256 over the frames' SHA-256 digests, for a mix or the session's randomness, never a key alone. The procedure is Faraday's own, and three frames per 128 bits is a heuristic; the frames only add to a mix or to the system's randomness, never make a key alone. (F158) Combines two to five sources, dice or this device among them, by hashing their commitments in the order taken. The specification is Faraday's own: SHA-256 over the concatenated commitments. With dice or this device among the sources, each at its full count, it only adds to that member's strength. (F158) Own specification, not yet reviewed outside Faraday (F160, F177).
  5. Makes an owner's Secure Boot keys, PK, KEK and db as RSA-2048 with self-signed certificates, and the enrolment files: signature lists, PKCS #7 signed updates and certificates. An RNG adapter written here, ChaCha20 (RFC 8439) as a stream keyed by a fresh 32-byte draw with the purpose in the nonce's first byte, feeds a pre-1.0 release of the rsa crate; its keystream is checked against RFC 8439 and every key it makes by openssl pkey -check. (F158) Own specification, not yet reviewed outside Faraday (F160, F177).
