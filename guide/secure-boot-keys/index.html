    Your own Secure Boot keys

    The owner name, release and passphrases on this page are examples only. Secure Boot keys cannot be made again from seed words, so Faraday makes them inside the backup: planned at two places or more, written to each, and used for nothing that signs until every place is written. In Faraday Demo, Practice makes no Secure Boot keys: Make the key does nothing there (Faraday Demo).

    You end with
    your own Secure Boot keys, PK, KEK and db, made in a vault kept on two sticks at two places; their enrolment files on a stick; release 0.1.8's boot program signed with your db key; and a Faraday stick that Faraday Starter wrote with that signed boot file, to start with Secure Boot on where your db key is enrolled.
    Before you start
    Vaults, passwords and codes (creating and unlocking a vault), Files, sticks and QR codes (a stick visit), Get Faraday on a stick and Start a PC from the stick.
    You'll need
    • Faraday started from the stick, with no stick attached but the Faraday stick.
    • Two USB sticks other than the Faraday stick, formatted FAT32, one for each place the keys are kept at.
    • A phone or watch showing the time to the minute: the certificates and the enrolment files carry the time they were made.
    • A computer with Faraday Starter and the release's files: faraday-0.1.8-BOOTX64.EFI, SHA256SUMS and SHA256SUMS.asc.
    • For enrolling: a computer whose firmware setup takes keys of your own, and, where Windows uses BitLocker, its recovery key.
    Time
    about 45 minutes, and the computer's firmware setup.

    The pictures of steps 8 and 9 sign a test release, 0.9.0, whose sums are signed by a test key; the steps are the same for 0.1.8. The Starter's picture in step 10 shows its own sample file.

    Faraday never writes a setting of the computer: the keys are enrolled in the firmware's own setup screen, from the files Faraday writes to a stick.

    1Start

    Press Tools, then Secure Boot keys (PK, KEK and db; sign an EFI image). With no vault open, the backup flow opens at once. With a vault open, Vault contents opens on Secure Boot instead: press Make keys there (Vault contents). An empty vault offers Make Secure Boot keys too.

    The flow's cards are those of A GPG key: Where it will be kept, Bring in the sticks, Vaults, Make the key, Lock, Write the sticks and Done.

    2Where, the sticks and the vault

    These steps are the same as a GPG key's (the backup flow):

    1. Where it will be kept: Vault 1, new, on a stick at Place 1 and another at Place 2. Two places or more; Add a place for a third. Press Continue (A GPG key, step 2).
    2. Bring in the sticks: Stick 2 for Place 1, This is the stick for Vault 1 (Place 1), mark it and pull it; then Stick 3 for Place 2, with a hold where it reads as the first (A GPG key, step 3).
    3. Vaults: Create Vault 1, its passphrase, Create vault (A GPG key, step 4).

    3Make the keys

    Under Owner name, type Example Org. The name goes into each certificate, as Example Org PK, Example Org KEK and Example Org db; left empty, the certificates read Faraday PK and so on.

    Press Make the key. The first time after power-on, Set the time opens first (Set the time): type the next minute and press Set when the phone's minute changes to it (Vaults, passwords and codes). Then press Make the key again. Making the key shows while the three RSA keys are made.

    The card reads Secure Boot keys made, in the ok tone:

    RowWhat it is
    Owner GUIDthe GUID the keys are listed under in the firmware
    PK, KEK, dbeach certificate's name: Example Org PK, Example Org KEK, Example Org db
    In Vault 1the vault the keys are in

    Press Continue.

    4Lock, and write the sticks

    The Lock card lists what the lock keeps (Kept) and wipes (Wiped from memory). Press Lock and write.

    Write the sticks asks for "Insert Stick 2: Vault 1 (Place 1)", then "Insert Stick 3: Vault 1 (Place 2)", as A GPG key, step 6 does: the first stick is refused for Place 2, and the second takes Hold: this is a second stick. Each copy is written, read back and compared (Written and checked on the stick's name).

    The enrolment files, made with the keys, go on the last stick written, once every other place is written. With the keys made in the flow, they are the Windows-compatible set (step 6).

    Done reads Written, with a line per stick ("Stick 2 · Vault 1 (Place 1) · KEYSTICK ·" and the time) and the files written to it: Vault-1.fvlt on Stick 2; Vault-1.fvlt and the nine enrolment files on Stick 3. Press Unlock Vault 1, type the passphrase and press Unlock.

    5The keys' page

    The vault opens on Secure Boot, and the keys' page is Owner keys (PK, KEK, db) (Secure Boot keys):

    Row or buttonWhat it is
    Owner GUID, PK, KEK, dbthe owner GUID and each certificate's name
    Enrolment addsWindows-compatible or Own keys only, and the line under them (step 6)
    BackupWritten to every place
    Enrolment filesthe enrolment files for the choice made, in Files for the stick
    Sign or check an imagethe EFI images in Files (steps 8 and 9)
    Hold to delete from vaultremoves the keys from the vault open

    Until every place is written, Backup reads "Written to 1 of 2 places" with Continue the backup, and Back up first stands in place of Enrolment files and of each image's Sign. Keys in a vault unlocked from its stick sign at once.

    6The enrolment files

    Enrolment adds decides what the files put in the firmware beside your own keys:

    ChoiceThe line under it
    Windows-compatible"Yours, with Microsoft's KEK CAs and Windows CAs. Not Microsoft's third-party CA: a card or controller whose firmware it signed may not start"
    Own keys only"Your PK, KEK and db only. Windows will not start, nor any card or controller whose firmware Microsoft signed", in the warning tone

    Choose, then press Enrolment files. Nine files go into Files for the stick:

    FileWhat it is
    PK.auth, KEK.auth, db.autheach store's signed update: PK signed by PK, KEK by PK, db by KEK
    PK.esl, KEK.esl, db.esleach store's signature list
    PK.cer, KEK.cer, db.ceryour three certificates

    Firmware setups differ in which of the three forms they take. Write the files to a stick on the next stick visit (Files, sticks and QR codes).

    7Enrol the keys

    Enrolling is done in the computer's firmware setup, from the stick, not by Faraday. Where the setting is, and which files a setup takes, differs by maker and model; Faraday has no page per maker for it yet.

    • Add the db key beside Microsoft's where the setup allows it; then both Windows and Faraday start with Secure Boot on. On some laptops, removing Microsoft's keys stops the graphics firmware loading.
    • Enrolling a key changes what BitLocker measures exactly as turning Secure Boot off does, and Windows may ask for its recovery key at its next start: have it ready (What Secure Boot and BitLocker are).
    • Surface computers and Macs take no keys of their own.

    The release's boot program carries no signature, so a computer that enforces your keys starts the stick only once its boot file is signed with your db key (steps 8 to 10).

    8Sign a release's boot program

    On the computer, download release 0.1.8's faraday-0.1.8-BOOTX64.EFI, SHA256SUMS and SHA256SUMS.asc, and put the three on a stick: the Faraday stick's data partition or another stick. On Faraday, copy the three in on a stick visit (Files, sticks and QR codes).

    Unlock Vault 1, open Secure Boot, Owner keys, and press Sign or check an image.

    Sign or check an image lists each EFI image in Files with Check and Sign; "No EFI image from the stick" while there is none. Press Sign on faraday-0.1.8-BOOTX64.EFI.

    The page reads "Sign faraday-0.1.8-BOOTX64.EFI", with the file's SHA-256 in groups of four and, under it, what Faraday found:

    LineThen
    "The boot program of release 0.1.8, checked against its signed sums"Hold to sign and Back
    No signed sums from a Faraday release are beside this filecopy in the release's SHA256SUMS and SHA256SUMS.asc
    The release's sums are not signed by Faraday's release keythe sums are not the release's: download them again
    "This file is not the boot program of release 0.1.8"the file is not the one the sums list: a changed file, or one already signed
    "Release 0.1.7 is older than this Faraday (0.1.8); sign a release at least as new"an older release; sign it on that release's Faraday
    This file is not an EFI imagenot a boot program

    With a refusal, the line is in the error tone and only Back is offered. The SHA-256 is the plain SHA-256 of the unsigned file, the one SHA256SUMS lists: compare it with the release's line.

    Hold Hold to sign until it fills. The signed file goes into Files for the stick under the same name ("faraday-0.1.8-BOOTX64.EFI, signed, waits for the stick"). Write it to a stick.

    9Check an image

    Check on an image's row says under the list what its signature is, against this vault's db key:

    ResultMeaning
    Signed by this vault's db keysigned with your db key, unchanged since
    Signed by another keysigned, by a key other than this db key
    Changed since it was signedthe signature no longer holds over the file
    Not signedno signature: the release's own file reads so
    Its signature could not be reada signature Faraday cannot read

    Back to the keys closes the images. A signed file is checked once it is copied in from a stick.

    10The Starter writes the signed boot file

    On the computer, put the signed faraday-0.1.8-BOOTX64.EFI in the Downloads folder. In Faraday Starter, press Make, then Make a Faraday stick; on For which computer?, A PC or an Intel Mac; on Which stick?, the stick (Get Faraday on a stick).

    On What to write?, choose New Faraday stick or, for a Faraday stick, Replace Faraday, keep data. Under Boot file:

    ChoiceWhat it is
    The release's (unsigned)ticked at first
    One I signedBOOTX64.EFI signed with your db key: lists the .efi files in Downloads, .EFI too, the newest first ("In" and the folder; "No .efi file in" and the folder while there is none)

    Press One I signed, then the file; a file dropped on the window is taken too. Checking against this release shows while the Starter checks it, then:

    RowWhat it is
    Certificate namethe name on the signing certificate: Example Org db (the picture's sample reads Faraday db)
    Certificate SHA-256: compare it with your db key'sthe certificate's SHA-256
    Filethe file taken

    The name is whatever the file's maker chose; the SHA-256 says whose key signed it. Compare it with the SHA-256 of db.cer from step 6 (sha256sum db.cer). A file the Starter refuses says why:

    RefusalMeaning
    This is not this release's boot fileanother release's program, or one changed
    This boot file is not signedno signature
    This boot file has no signature that holdsa signature that does not hold over the program
    This boot file holds more than the release's program and one signaturesomething more than one signature added

    Continue waits until a signed file is taken. Confirm lists the Boot file with the certificate's name and SHA-256; press Erase and write (a new stick) or Write (keep data). The Starter writes the release's own program with your signature in place of the release's file; it reads the file again before writing, and refuses it if it changed after it was chosen.

    Without the Starter, once the stick holds the release, copy the signed file over EFI/BOOT/BOOTX64.EFI on its boot partition, the first, labelled EFI (Faraday's README, "With Secure Boot").

    11Start with Secure Boot on

    On the computer whose firmware holds your db key, start from the stick with Secure Boot on (Start a PC from the stick, leaving out turning it off). Each new release's boot program is signed again, as in steps 8 to 10, on a Faraday no newer than that release: the Faraday stick you have signs the next release's.

    With your own key

    • Make the keys on the Faraday stick, not in Faraday Demo, which runs on a computer with a network.
    • Never enrol keys you have not backed up: wait until the key's page reads Written to every place, then unlock the vault once from each stick on a fresh start (Before you rely on a key). Without the db key, no new release can be signed for that computer.
    • Keep Microsoft's keys (Windows-compatible) on a computer that runs Windows.
    • Have the BitLocker recovery key at hand before enrolling.
    • Compare the certificate's SHA-256 on What to write with your db.cer before writing a stick.
