Audits

Faraday invites audits from experts and AIs. Each one is published here with Faraday's response to every finding, and the full prompt and output.

What an audit includes

By an expert or an AI. This list is not a prompt by itself: write your own prompt for the audit, then add this list at its end.

Faraday's request for this audit. Follow it in the output:

1. Record what was audited: the repository (https://github.com/bitcoinpasada/faraday), the commit (git rev-parse HEAD), the date, any tools run, and for an AI, the model and its version.
2. State the scope: the areas covered, the parts of the code read, and the parts not read. docs/AUDIT.md lists where the cryptography is.
3. For each finding, give: a severity, the file and line, what goes wrong, how to trigger it, and whether it was confirmed by running code or only found by reading.
4. Write the output as Markdown in two files: audit.md for everything except critical and high findings, and private.md for critical and high findings only. Leave out private.md if there are none.
5. End audit.md with a summary of at most 150 words: what was examined, what was found, and an assessment of whether the code can be trusted with keys. If private.md exists, the summary gives its number of findings without describing them.
6. Redact personal information from both files: names, email addresses, usernames, and anything about the computer the audit ran on, including home directory paths, hostnames, IP addresses, the operating system and its version, hardware, and environment variables. Replace each with a placeholder such as <home>, <user> or <host>. Leave unchanged the names and addresses in Faraday's own code.
7. If private.md exists, hash it last, after step 6: run sha256sum private.md > private.md.sha256. If you cannot run commands, do not write a hash; say that it still needs to be made.

Severities:
- Critical: a key, seed or passphrase can be extracted; the device signs, or shows as approved, something the user did not approve; Faraday's output is wrong in a way that loses funds (an address it cannot spend from, a backup or shares that do not restore); or crafted input runs code on Faraday.
- High: the same, but only under specific conditions (physical access, a non-default setting, a rare input); a vault slot opens without its passphrase or reveals how many slots are used; the air gap fails; secrets outlive the session; a tampered image or upgrade is accepted; Faraday Starter writes to the wrong disk; the design makes a mistake that loses funds or exposes a key likely, through a missing warning or confirmation or a misleading label.
- Medium: a protection is weaker than intended but holds (a lower key-stretching cost); a crash from crafted input with no code run; public wallet data leaked.
- Low: a defect with no direct security effect, including a wrong result that Faraday detects and refuses.
- Note: an observation, not a defect.

Areas to cover

A starting point for the audit's scope. Add them to the prompt as they are, change them, or write your own.

Areas to cover:
- Key material: whether a key, seed or passphrase can leave the device; the randomness and entropy behind key generation; nonces in ECDSA, Schnorr and MuSig2 signing.
- Signing: whether what the screen shows (amounts, fee, destinations, change) is what gets signed.
- Correct results: derivations, addresses, mnemonics, SLIP-39 and codex32 shares, KDBX backup files and MuSig2, against published vectors and other implementations.
- The vault: each slot's passphrase opens only that slot, the key-stretching cost is the one stated, the file does not reveal how many slots are used, and a damaged file is detected.
- The air gap and what remains: no network interface comes up, secrets are written only where the user chooses, and none outlive the session.
- Untrusted input: PSBTs, QR codes, images and file systems from the online computer.
- The image and its tools: release verification, the Secure Boot keys, the upgrade, and Faraday Starter's disk writing and checks.
- Access: the keyboard code and the passphrase prompts.
- Mistakes a person can make: where Faraday or Faraday Starter make an easy mistake possible that loses funds, exposes a key or locks a person out of their computer: a misleading label, steps in a confusing order, a risky action with no confirmation, a risky setup with no warning (a TV, a capture card or KVM, a wireless keyboard), a backup that can be skipped or left unchecked, and whether the warnings that exist come at the moment they are needed.
  • An expert audit has no prompt.md: audit.md describes its method.
  • The files carry no names. A name or pseudonym for credit goes in the issue form.
  • docs/AUDIT.md lists what Faraday computes, what is written in its own code and what comes from libraries.
    docs/AUDIT.md

What Faraday does

The same timeline is in the repository's SECURITY.md.

Within 15 days

A reply on the issue

The hash quoted back, and a verdict on each finding: confirmed and fixed, with the fixing commit; confirmed and open; could not reproduce; or not a bug.

Within 15 days

A private report with no issue

A reply on it within 15 days of its arrival.

Then

The entry, published

The submitter's summary, unedited, Faraday's short response, and the full prompt and output, below.

Once fixed

private.md, published

No later than 90 days after the private report, fixed or not. Anyone can check it against the hash posted on the issue.

The release's cross-check

Faraday's rule for what goes into the app (STANDARDS §0) is that what makes or reads a key, a secret, an address, a signature or a transaction is checked against an implementation Faraday did not write. Each release carries the record of a full cross-check run on its tree.

crosscheck-0.1.9.txt

Each cross-check area with its cases, answers and result; every outside reference with its commit and SHA-256; the seed, to run it again; and the git tree checked, which git rev-parse v0.1.9^{tree} gives for the release's tag.

Not shown in the record

Areas against Faraday's own models

Some areas still compare Faraday's Rust with a model written by Faraday's own authors. The Cryptography page names each action's reference and whose code it is.

crosscheck-0.1.9.txt How the cross-check runs Cryptography

Outside review of Faraday's own constructions

Some of Faraday's cryptography follows no published standard. Each such action carries the label "own construction, not yet independently reviewed" until someone outside Faraday reviews it. Anyone who is not one of Faraday's authors, or an agent working for them, may answer this call. No reviewer is chosen.

The cross-check compares Faraday's Rust there with a model written by Faraday's own authors. That catches a slip between two transcriptions of one text. It does not catch a misreading both share, or a flaw in the text itself. The label is shown in the app's and the Cryptography page's blocks and in STANDARDS §7.

The vectors of own randomness, the cards, the camera, a mix and the rollers are a JSON file each, beside a README that says what each vector covers and how it was made, and gives the construction in words and a few lines of Python, standard library only, that reproduce its answers. Faraday's tests read the same files.

What is asked

One or more of these, for one construction or several.

1

An outside model

A second implementation, written from the spec alone, without reading Faraday's code for it. It reproduces the vectors and known answers, and offers the operations below, so that it can take the place of Faraday's model in the cross-check. Each place where the spec leaves the answer open, and each disagreement between the model and the vectors, is a finding.

2

A reproduction of the vectors

Your own code, in any language, opening or computing each vector, with the answer it gives for each.

3

A review of the construction

Whether it does what its spec says: for the vault, the promises of VAULT §9; for own randomness, that what a person adds cannot lower the system's randomness; for cards, the camera and a mix, that the bits counted are there; for the Secure Boot generator, that the keys are drawn as F134 and F158 state. Findings take the severities above.

For the Secure Boot keys and a key held in memory, the review is what is asked: a model would have to reproduce the rsa crate's own search for primes to match the known answers, and the in-memory seal is reached by no shipped code.

What a model offers

A model the cross-check can call is:

  • Python 3, over the standard library and the packages the cross-check already takes from the distribution (argon2-cffi, PyNaCl, PyCA cryptography), fetching nothing at run time, with no file over 2 MiB;
  • under a licence that allows copying it unchanged into Faraday's repository: MIT, BSD, Apache-2.0, CC0 or public domain.
  • A model in another language counts as a reproduction. Running it in the cross-check needs its toolchain allowed by a decision, as Go was for LND's aezeed.

The operations each area compares

  • The vault. Open a file with a passphrase, giving the slot that opens, its seal count and its records, or the refusal that applies; make a vault from its passphrases, cost, slot size and records with every random byte given (the salt, the order of the slots, the nonces and the bytes of the unused slots), so the file is compared byte for byte; seal an open slot under a given nonce and time; write and read a slot's records, with each refusal.
  • Own randomness. Its operations over given system answers: a batch added, the seed, a fresh answer for a purpose, a seed draw, This device's answer, a lock; and its commitments.
  • Cards, camera and a mix. Each source's commitment and its entropy at each strength, with the refusals the procedures state.
  • The rollers. The values made from given answers; the one die's clicks and the five dice's worksheet, as CODEX32 §5.5 and §5.6 state them.

Faraday's side, to compare with

Once the model is written. The prerequisites are in docs/DEVELOPING.md.

The records of the slot a passphrase opens, over argon2-cffi and PyNaCl, or cryptography:

python3 tools/vault/open.py tools/vectors/vault/vault-three.fvlt

One area of the cross-check: Faraday's Rust against the reference the area names, over a corpus drawn from a seed, which it prints. The second command runs case N of it again.

just crosscheck --area vault
just crosscheck --area vault --seed S --case corpus:N

The known answers, over the files in tools/vectors/. Each of those folders' README also checks its file with Python alone.

cargo test -p faraday-core --test all own_randomness
cargo test -p faraday-core --lib five_tests
cargo test -p faraday-entropy
cargo test -p faraday-sb

Submitting a review

As any audit, with the audit form. Its model field is "expert", or the model and its version where an AI wrote the model or the review under the reviewer's direction.

audit.md says:

  • which construction, and which of the three was done;
  • for a model, that it was written from the spec without reading Faraday's code for it, where it is (a public repository at a commit, or an archive attached to the issue), its licence, and how to run it;
  • the answer for each vector and known answer, and where it differs from the file;
  • the findings, by the severities above. Critical and high findings go in private.md.

How a result is recorded

The entry here

As any audit's, and it also names the construction, the kind of review, and for a model its repository, commit and each file's SHA-256.

Faraday's reply

A verdict on each finding, on the issue. A disagreement between the model and Faraday is settled by a fix to Faraday, or by a change to the spec where it left the answer open or was misread.

The decision

Whether a submission counts as the outside review of a construction is the owner's call. A decision records the reviewer as credited, the construction, the commit reviewed and the kind of review, and says whether the construction stays on the list for outside review. With it the action's label goes.

A model, in the cross-check

Copied unchanged into tools/reference/ with its source, commit, licence and each file's SHA-256. The area compares Faraday with it in place of Faraday's own model, which is retired. Where the comparison is wholly against it, the Cryptography page names the reviewer as the reference's author. A reproduction or a review alone takes the label away with the decision; the area's reference stays Faraday's own model.
