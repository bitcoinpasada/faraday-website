The vault

A vault keeps your secrets encrypted under a passphrase, so a copy can sit on a stick or on paper and nobody can read it without the passphrase.

Faraday's vault is a file. It holds everything you keep in Faraday. The app also makes two codes, Krux's KEF and the QR vault, because a file cannot do one job: keep a single seed on paper, as a QR code you can print. A third code, a proposal, is not in the app. A code has little room, so each of the three trades size against how hard a stolen copy is to guess.

Which one, and when

Four forms, one for everything and three for a single secret on paper.

The file vault In the app

A file on a stick holding seeds, wallets, entries, notes, and GPG and Secure Boot keys, under Argon2id, with a key file or a YubiKey's secret as an option. It is the vault to use for anything more than one secret on paper.

Krux's KEF In the app

A small code, 33 × 33 for 24 words, that a Krux device can also read. For when a code has to open on a device with very little memory. It uses PBKDF2, which costs no memory, so it asks more of the passphrase.

The QR vault In the app

A large code, 77 × 77, holding one item under Argon2id, in standard formats other programs open. For when one secret on paper should cost a guesser memory, and should open without Faraday.

The proposal Seeking outside review

A code about the size of a SeedQR, 29 × 29, under Argon2id. Nobody can choose this one: it is a draft with test vectors and a Rust implementation by the same authors (a library, a command line and a desktop test app), with no outside one, and it stays out of the app until it has been reviewed.

Each form's facts are from its specification: the file vault and the QR vault, KEF, the proposal.

The file vault: two layers

What keeps secrets safe, and what lays the file out.

The lock

The passphrase, Argon2id, ChaCha20 and HMAC-SHA-256. This is what keeps secrets safe. All of it is published, and each algorithm comes from an established library: argon2, chacha20, sha2 and hmac.

The plumbing

The code that lays the file out, reads it back and decides which field holds what. Most of what is Faraday's own is here. A bug here usually means a file that does not open. The exception is under Security.

The file vault's format

KDBX 4.0, as KeePass's specification says.

The passphrase, with a key file or a YubiKey's secret if the person adds one. The file does not record that it needs either.
The passphrase
Put in Unicode NFC first. Nothing else is done to it: no character is mapped or refused, and case and spaces are kept as typed.
Its name
.kdbx. A file is recognised by its contents, whatever its name.

Each of Faraday's items is a KeePass entry whose custom data names its kind. Custom data is part of KDBX 4, inside the encryption: any KDBX reader with the passphrase reads it. An item that is damaged does not refuse the file: it is named as Unreadable, never loaded or used, and written back as it was read.

A key file and a YubiKey's secret

Key file
Optional, added when a vault is made or from the open vault's menu, and taking effect at the next seal. Faraday makes one as KeePass's XML version 2 (.keyx) holding 32 random bytes, written to the Outbox, or takes any file from a stick. If it is lost or changed, the vault cannot be opened.
YubiKey
A KeePassXC file whose key is programmed for HMAC-SHA-1 challenge-response with variable input opens with the key's secret, typed as 40 hexadecimal digits at unlock. Faraday never sets a YubiKey up, and a vault opened without a secret cannot be given one. The open vault's menu has Remove YubiKey secret.
How they combine
The key file's key and the secret's response go into the composite key with the passphrase, so Argon2id stretches all of them. The passphrase is always one component: a file with none is refused. Reading a key file follows KeePass's rules, checked against keepassxc-cli and pykeepass; the YubiKey's response is checked against kdbxweb, KeeWeb's library, and not yet against KeePassXC's own test file.

Size and memory

A file vault grows by itself. Its memory step is chosen when it is made and can be changed on an open vault, taking effect at the next seal.

Size

There is no size to choose. A new vault holds 32 KiB of contents, and each seal pads them to the smallest multiple of 32 KiB that holds what the vault holds, up to 128 MiB. It shrinks the same way when it holds less.

VaultContentsFile

Largera multiple of 32,768 Bthat, plus 313 B of header and 36 B for each 1 MiB block and the empty block after them

Faraday pads with line feeds after the document's closing tag, which XML allows, so a file Faraday sealed says by its length only how much it holds, to within 32 KiB. A KeePass app's save drops the padding, so the length of a file saved there says more until Faraday seals it again. A file with contents up to 128 MiB opens, whatever its length.

Memory comes before size. Faraday checks what the computer has free before it reads a file from a stick, before an unlock, once the contents are decrypted and before a seal, and says so instead of starting. A seal that does not fit stops a lock: the vault stays open with its changes and the Lock sheet names what is short.

The memory free to open is for a new vault's 32 KiB file: Argon2id's memory, twice the file and 100 MiB, and each further MiB of the file adds two. Bits added is log2(memory in KiB × passes), an estimate that counts work only. The Pi 3 image is 32-bit, where one allocation of 512 MiB or 1 GiB may fail even with the memory free.

Memory is a hard limit, time is not

A machine without the memory cannot open the vault at any speed; a slow machine opens it slowly. So the step is chosen for the weakest machine the vault will ever be opened on. Faraday says when a vault does not fit, before the passphrase is typed.

The passphrase matters more

Doubling the memory is worth one bit of passphrase strength, and the five steps span four bits. One more word from the EFF long list is 12.9 bits. A six-word dice passphrase, 77.5 bits, is out of reach at any step here; a short or reused passphrase is not protected by any step here.

Where the numbers come from

RFC 9580 recommends Argon2id with 3 passes, 4 lanes and 64 MiB where 2 GiB cannot be spared, and RFC 9106 gives the same choice. The steps above 64 MiB keep its passes and lanes and raise its memory. Lanes do not change the work of a guess.

Sealing

Sealing writes the open vault back as a file, at every lock.

Every seal is a new file

Every seal draws a new master seed, encryption IV, Argon2 salt and inner stream key from the system's randomness, mixed with whatever the person added through Add randomness. Argon2id runs again. A seal waits for the randomness it needs and never stretches less.

Every seal is a new file, so an open vault's passphrase, memory step and key file can each be changed. Copies sealed before keep theirs.

Read back before it is given

The file is opened again under the keys it was made under, and its contents must be the ones written. A file that fails is not given, and the vault stays open with its changes.

The seal count

The count and the time of the last seal are in the database's custom data, inside the encryption. The app keeps the highest count it has seen of each vault. Opening an older copy stops at a dialog, Open this copy?, which names the vault and the copy it saw.

Writing to a stick

The sealed file is written beside the original and read back byte for byte before the original is deleted. FAT has no atomic replace: if a visit finds both, it keeps the original when it reads back whole and discards the new file; otherwise the new file is the vault and takes the original's name. A file of the same name that is not an earlier copy of the vault stays, and the seal goes beside it as name-2.kdbx.

What it promises

And what it does not.

Without the passphrase
A vault shows that it is a KDBX 4 database, its Argon2id cost and its length, which says how much it holds to within 32 KiB; nothing of its contents.
A changed byte
Refuses the whole file: the header's HMAC and every block's HMAC are checked before anything is read. A KDBX file opens to one content whichever passphrase opens it, since its HMACs are keyed from the passphrase's key.
Slots and decoys
A vault has one passphrase and no slots. A decoy is made inside a wallet's own standards: a BIP-39 passphrase gives another wallet from the same words. A vault opened under pressure shows what it holds.
Rollback
Whoever can write the stick and holds an older copy can put it back. Its contents cannot be altered, but they can be replaced by an earlier state of themselves. The app names a copy older only when the session has seen a newer one since power-on, or an open vault's backup plan records one. It cannot tell otherwise.
Damage
A vault is checked when it is opened. A damaged file loses it all. A copy at another place is the remedy.
Offline guessing
Anyone with the file has its salt and cost and can try passphrases on their own computers, each guess costing one Argon2id at the vault's step. A vault is as strong as its passphrase. A key file or a YubiKey's secret adds 256 or 160 bits for whoever lacks it, and a person who loses it and has no copy loses the vault.
Not done
After the first half of its first pass, Argon2id reads memory at places the passphrase decides, a cache-timing side channel on the computer that unlocks. Later work.

Other programs

A vault is a standard file. It is meant to be opened in Faraday, on the offline device.

What has been tried

pykeepass, keepassxc-cli and keepass-rs open what Faraday writes. KeePass, KeePassDX and Strongbox read the format and have not yet been tried on it.

The caution

Unlocking a vault on a phone or computer connected to the internet shows its seed on that machine. It is a last resort, if Faraday is gone and the seed is needed back: do it once, move the funds to a new seed, and treat the old one as exposed.

Security

What each custom part means for the secrets in a vault.

What protects secrets is all published

An attacker with the file faces Argon2id at the vault's memory step, then ChaCha20. None of that is Faraday's design.

The main risk is parsing

The device reads files from outside. A reader bug could crash, hang, or wrongly accept or refuse a file. The guards: limits checked before any work (memory 8 MiB to 1 GiB, passes 1 to 100, lanes 1 to 64); an XML reader that refuses a DOCTYPE and unknown entities; a fuzz target for each reader.

The one subtle risk is in writing

If Faraday's code reused a value it should draw fresh, a nonce say, the file would still open everywhere, so opening it elsewhere would not notice, but the encryption would be weaker. A library carries the same risk in its own code. The guard: every seal draws its bytes from one call for the session's randomness, and the specification counts every byte that call returns.

The library trade

A large library is more code Faraday did not write and more to vet, looked at by others. A small piece of Faraday's own is less code and nothing extra to vet, looked at by Faraday and its tests.

How it is checked

Against published vectors and a reader Faraday did not write.

Vectors
Vaults holding every item kind, each with a known passphrase, and one file refused for each rule, published for any implementation to open. Faraday's Rust reads them, and so does a reader over pykeepass. The QR vault's vectors are Faraday's own, not an outside check: one of each item kind, an empty one, one made with a passphrase in NFD and four refused messages.
Cross-check
The vault area runs pykeepass and keepassxc-cli both ways: each opens Faraday's files with every field, group and attachment, Faraday opens theirs with the same fields, and each refuses a wrong passphrase and a changed byte. KeePassXC ends a protected value at its first NUL, which Faraday keeps: a known difference, counted. The area also compares the payload layouts, a passphrase's NFC form and Argon2id with outside code, and reads key files against keepassxc-cli and pykeepass.
QR vault
Its own area: Faraday's seals are opened by Sequoia's sq, by rPGP and by a judge over PyCA cryptography, and what they make is opened by Faraday. sq cannot seal one, as it writes only the older OpenPGP packets, so the area checks that Faraday refuses what sq writes. The judge's framing is Faraday's own second version, not another program's.
KEF
Every version, each way, against Krux's own code, taken unchanged and run in software, over Krux's own test vectors. Not on a Krux device.
Fuzzing
Fuzz targets, seeded from the vectors, for the KDBX header and block stream, the padding, the inflate and the inner header, and the XML reader; the QR vault's packets and contents; and KEF.
Outside review
Faraday's names inside the vault are its own specification, not yet reviewed outside Faraday. The Audits page asks for that review.
Each action
The cryptography page lists what each vault action follows, the code it runs and what it is compared with.

Krux's KEF In the app

The Krux project's encrypted code: small enough for 33 × 33, opened by a Krux device or by Faraday.

What it is

KEF, the Krux Encryption Format, is an envelope for encrypted bytes: a label, a version, a PBKDF2 count and an AES payload. Krux publishes its specification, with its own code as the reference.

The cryptography is standard. The format is one project's: it is not a BIP, a SLIP or an RFC, no other implementation was found, and no outside review of it is known.

The envelope

len_id | id | version | count | payload

The key is PBKDF2-HMAC-SHA-256 of the passphrase, with the id as the salt, 32 bytes, always for AES-256. The id, the version and the count are in the clear. Krux's default id is the wallet's fingerprint.

What Faraday does

Reads and writes all twelve versions as Krux v26.09.0 does, and writes version 20 by default with a random 8-byte id, not the fingerprint: a fingerprint on a printed code says which wallet it opens, and gives every code of a seed under one passphrase and count the same key. The default count is 100,000, Krux's, and 10,000 to 500,000 is offered. Versions 0 and 1 are written as legacy.

Reads a code as raw bytes or as hex, base32, base43 or base64 text. Writes base43 at medium error correction for anything that fits one code, and refuses larger contents. The passphrase on writing is printable ASCII, 1 to 200 characters, stricter than the vault's, since a code has to open on a device with a small keypad. Left out: Krux's seeds.json store, and a passphrase that is itself a KEF code.

Faraday scans a code and makes one from a seed or in Tools. It is checked both ways against Krux's own code, in every version, running in software. It is not checked on a Krux device, since the project has none: that a device's AES engine gives the same first 4 tag bytes rests on Krux's claim of compatibility.

PBKDF2 is not memory-hard

A guess costs count runs of HMAC-SHA-256, which specialised hardware does very quickly, and it needs no memory. Krux's default of 100,000 adds about 16.6 bits to a passphrase as work, and 500,000 about 18.9. Argon2id at 64 MiB to 1 GiB adds about 17.6 to 21.6 by the same count, and also needs its memory for every guess, which that count does not show. OWASP asks for 600,000 for PBKDF2-HMAC-SHA-256, more than Krux's setting allows.

The specification says it plainly: "KEF offers no expectation of security for a weak user-supplied key."

A short check is not proof

A check of 3 or 4 bytes says the passphrase was probably right. A wrong one passes about 1 time in 16,777,216 (version 5) or 4,294,967,296 (the 4-byte versions), and what comes out is random bytes. Sixteen or 32 random bytes are a valid seed, so the person compares the wallet's fingerprint with what they wrote down.

The length shows

KEF has no padding: Krux has to be able to read the contents as they are. A code's size says whether it holds 12 or 24 words, and a note's size says its length.

What it is for

A short code, opened by a Krux device or by Faraday, including on a device with very little memory. A code can be copied unnoticed and attacked for ever, so the passphrase is the whole of the protection.

The QR vault In the app

One item at 77 × 77, memory-hard, in standard formats outside programs read.

What it offers

Every guess costs Argon2id's memory, 64 MiB to 1 GiB. Every code has full 16-byte tags, not a cut check. It is padded to one size, so a code does not show what it holds, or whether it holds anything. And it opens without Faraday.

It holds one 12- or 24-word seed, one codex32 share, one BIP-39 passphrase with the fingerprint of its key, or a short note.

All of it standard

A QR vault is an RFC 9580 OpenPGP message under a passphrase: one SKESK v6 packet with the Argon2 string-to-key, and one SEIPD v2 packet with AES-256 in OCB mode, holding a literal data packet. OCB is the one AEAD RFC 9580 requires every implementation to have.

The contents are a TOML v1.0.0 document padded to 226 bytes. Which keys it uses is Faraday's own rule, since no standard exists for this. The message is 396 bytes: QR version 15, 77 by 77 modules, at medium error correction.

Why OpenPGP

A QR vault has to fit a code a phone reads off a small screen or a print. The smallest KDBX file holding the same seed is about 1,140 bytes, QR version 28, 129 by 129 modules. So the code uses RFC 9580, and the file vault KDBX.

Every seal is a new code. A code printed before still opens, to what it held when it was sealed, so a new code means destroying the old one.

Opening one without Faraday

Sequoia's sq, GopenPGP, OpenPGP.js and rPGP open it. GnuPG does not, since it follows LibrePGP rather than RFC 9580.

On a computer, save the code as its bytes with zbarimg --raw -Sbinary code.png > vault.pgp, then sq decrypt vault.pgp. Read as text, the bytes are mangled and Sequoia refuses them.

On Android, the camera app and Google Lens read a code as text. A scanner that gives raw bytes and an app that reads RFC 9580 are both needed, and no mainstream Android app is known to read RFC 9580.

In the app

One tool in Tools makes and opens a code. A file vault's item, a seed, a codex32 share, a passphrase or a note, also offers Save as a QR vault. A code is never kept open: to change what it holds, a new one is made. Faraday Starter has no such tool.

A code scanned where a SeedQR is scanned, or a .pgp file chosen in Files, opens to a passphrase typed once, with its cost checked before the work starts. A seed's words go to the seed sheet, a share to Add a key, a passphrase to the key it belongs to and a note to an open file vault.

The picture is a PNG saved to the Outbox, labelled with "QR vault", the vault's name and the date, never what it holds. A code of 77 × 77 is not copied by hand: its paper is that PNG, printed from a computer with a printer.

What it costs

A large code: 77 × 77 cannot be copied by hand, and it needs a good print or screen. It needs 64 MiB or more to open, so a microcontroller signing device cannot read it.

OCB does not commit to its key, so a code made by someone else could be built to open to two contents under two passphrases. Faraday makes every QR vault under one.

A proposal: the Argon QR Vault (AQRV) Seeking outside review

A memory-hard code the size of a SeedQR. A draft: it has test vectors and a Rust implementation by the same authors, with no outside one, and it is not in the app.

The idea

Krux's KEF fits a seed in a small code under PBKDF2, which needs no memory. The Argon QR Vault (AQRV) is the same idea under a memory-hard function: one small secret under a passphrase, with Argon2id at 3 passes, 4 lanes and 64 MiB to 1 GiB, ChaCha20 and HMAC-SHA-256 cut short.

It is proposed as an open format. It carries no name of Faraday's and depends on nothing of it.

What it holds

A BIP-39 seed of any length, a codex32 string, a BIP-39 passphrase, a short note or a raw 32-byte key. The kind is not stored and the rest of the room is random, so a code does not show which it holds, within a size.

What it does not do

It does not make a weak passphrase safe: a code can be photographed and attacked offline. It does not open on most microcontroller signing devices, which lack 64 MiB. Its tag is too short to prove that an item is the one sealed, so a reader shows the wallet's fingerprint where the kind has one. KEF stays the form for small devices, and an OpenPGP code the form with outside readers.

The length says which size it is, and enters the tag. The longer tag is a better check for a person and a better test for a guesser, so at that size the passphrase has to stand alone.

A wrong passphrase that gets past the check does not open what the code holds, which stays encrypted. It decrypts to random bytes, and those usually read as a valid but different seed, so the person compares the wallet's fingerprint with the one they wrote down.

What is asked

Every primitive is published. The composition with a short tag is not a named standard, and that is the first thing a reviewer is asked about.

  • Is Encrypt-then-MAC with HMAC-SHA-256 cut to 32 or 64 bits sound here, where each check costs a person typing a passphrase?
  • Is a fixed zero nonce under a key derived per salt acceptable, or should it be synthetic?
  • Would AES Key Wrap be the better shape?
  • Does any realistic use make the lack of key commitment matter?
  • What do GPUs, FPGAs and ASICs achieve against these Argon2id settings?

Answers of "this is wrong" are wanted most of all. The specification lists all eleven.
